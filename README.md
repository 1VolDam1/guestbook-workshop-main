# Guestbook — capstone: от коммита до релиза

Небольшая гостевая книга на FastAPI и PostgreSQL, подготовленная как эксплуатационный проект курса: воспроизводимые зависимости, Docker Compose, CI, публикация образов в GHCR по `main` и SemVer-тегам, а также инструкция отката.

> Приложение и конфигурация уже подготовлены. Чтобы получить доказательство настоящего CI/CD и отката для защиты, перенесите этот каталог в свой GitHub-репозиторий и выполните сценарий «История релиза» ниже. Из этой среды нельзя создать/запушить релиз в ваш GitHub или развернуть его на принадлежащем вам сервере.

## Возможности API

- `GET /` — приветствие из `GREETING`.
- `GET /health` — liveness-проверка приложения.
- `GET /messages` — список сообщений, новые сверху.
- `POST /messages` — добавить сообщение, JSON: `{"author":"Ada","text":"Hello"}`.

## Требования

- Docker Engine с Compose plugin (локальный запуск и production-подобный стек).
- Для работы с зависимостями вне Docker: Python 3.13 и [uv](https://docs.astral.sh/uv/).
- Git и аккаунт GitHub для CI/CD и публикации GHCR.

## Запуск одной командой

```bash
cp .env.example .env
# Для локального использования можно оставить демонстрационный пароль;
# не используйте его на публичном сервере.
docker compose up --build -d
```

Проверка:

```bash
curl -fsS http://localhost:8000/health
curl -fsS http://localhost:8000/messages
curl -sS -X POST http://localhost:8000/messages \
  -H 'Content-Type: application/json' \
  -d '{"author":"Ada","text":"Привет!"}'
curl -fsS http://localhost:8000/messages
```

Сообщение хранится в именованном volume `pgdata`. Оно должно остаться после `docker compose down` и последующего `docker compose up -d`. **Не используйте `docker compose down -v`, если хотите сохранить данные.** Приложение ждёт успешного healthcheck PostgreSQL перед запуском.

Остановить стек, сохранив базу: `docker compose down`.

## Настройки и секреты

Список переменных указан в `.env.example`. Скопируйте его в локальный `.env` и задайте свой пароль. `.env` игнорируется git и Docker build context; коммитить нужно только шаблон `.env.example`. В `compose.yaml` пароль подставляется через `${POSTGRES_PASSWORD}`, а в контейнер приложение получает переменные окружения. В коде пароль не зашит.

Не используйте демонстрационное значение из шаблона на публичном/боевом сервере. Если реальный секрет когда-либо попал в Git, удаление файла недостаточно: немедленно смените секрет и сообщите ответственному.

## Разработка, линт и тесты

```bash
uv sync --locked
uv run ruff check .
uv run pytest -v
```

Тесты изолируют PostgreSQL и проверяют HTTP-контракт через FastAPI `TestClient`; отдельный интеграционный приёмочный тест выполните на Compose-стеке, как описано выше.

## Архитектура и инженерные решения

- `uv.lock` фиксирует разрешённые версии; `.python-version` закрепляет Python 3.13.
- Dockerfile устанавливает зависимости по lock-файлу **до** копирования часто меняющегося исходного кода, чтобы сохранять кэш слоёв. Секреты и `.env` отфильтрованы `.dockerignore`.
- Compose соединяет приложение и PostgreSQL по DNS-имени сервиса `db`; наружу открыт только порт приложения. PostgreSQL имеет healthcheck, приложение зависит от `service_healthy`, данные хранятся в `pgdata`.
- GitHub Actions запускает Ruff и pytest на push и pull request. Только после успешного `check` публикация из `main` обновляет `:latest`; push тега `vX.Y.Z` публикует неизменяемый образ с этим тегом. Используется временный `GITHUB_TOKEN`, личный токен в репозитории не нужен.
- Для маленького одноэкземплярного сервиса выбрана **контролируемая замена контейнера по точному тегу** вместо сложного blue-green/canary. Она проста и даёт быстрый обратимый откат, но может дать короткий перерыв доступности — это осознанное ограничение, а не заявление о zero-downtime rolling.
- Сейчас схема `messages` только создаётся через `CREATE TABLE IF NOT EXISTS`; разрушительной миграции нет. Будущие изменения должны следовать expand-contract: сначала добавить nullable-колонку/таблицу, переживающую старый код, затем перевести код и лишь позднее удалять старое поле. Образ можно откатить, состояние базы — нет.

## CI/CD и история релиза на GitHub

1. Создайте GitHub-репозиторий, перенесите туда **содержимое** каталога, установите default branch `main`, затем запушьте. В Actions должен пройти `check`; после зелёного check для `main` в Packages появится `ghcr.io/<owner>/<repo>:latest`.
2. Перед первым релизом обновите `CHANGELOG.md`: перенесите записи из `[Unreleased]` в `## [1.0.0] - YYYY-MM-DD` (укажите фактическую дату выпуска) и закоммитьте/запушьте их в `main`.
3. Создайте и отправьте аннотированный тег:

   ```bash
   git tag -a v1.0.0 -m "Release v1.0.0"
   git push origin v1.0.0
   ```

   Во вкладке Actions должны пройти `check` и `release`; в Packages должен появиться `:v1.0.0`. Версии в GHCR соответствуют точному коммиту тега.
4. Для показа отката подготовьте второй совместимый релиз (например, небольшое изменение текста приветствия), занесите его в changelog, обновите `main`, выпустите `v1.1.0` тем же способом. На сервере/учебной машине переключите `APP_IMAGE` с `...:v1.0.0` на `...:v1.1.0`, затем выполните:

   ```bash
   docker compose pull app
   docker compose up -d --no-build
   curl -fsS http://localhost:8000/health
   ```

   Чтобы продемонстрировать rollback, верните `APP_IMAGE` на `...:v1.0.0`, повторите те же команды и снова проверьте `/health`. Перед демонстрацией откройте Package settings на GitHub и сделайте образ публичным, если хотите тянуть его без авторизации. Для приватного GHCR выполните `docker login ghcr.io` с токеном, имеющим `read:packages`, не записывая токен в файлы проекта.

**Важно:** Compose-файл содержит `build: .` для локального запуска. При переключении `APP_IMAGE` на опубликованный образ сначала выполните `docker compose pull app`, а затем используйте `--no-build`, чтобы запустить именно версию из GHCR.
