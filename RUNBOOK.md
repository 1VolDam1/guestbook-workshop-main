# RUNBOOK — guestbook

Инструкция для дежурного. Выполняйте шаги по порядку. Не публикуйте `.env`, пароли или вывод с секретами в тикетах и чатах.

## Контекст и безопасные ограничения

- Стек: контейнер `app` (FastAPI) + `db` (PostgreSQL), запущенные Docker Compose.
- Внешние проверки: `http://<HOST>:8000/health`, `http://<HOST>:8000/messages`.
- Образы для эксплуатации задаются точным тегом `ghcr.io/<OWNER>/<REPO>:vX.Y.Z` через `APP_IMAGE` в серверном `.env`.
- Не выполняйте `docker compose down -v`: флаг `-v` удалит volume базы и данные.
- Для отката кода не откатывайте и не удаляйте volume PostgreSQL.

## Сервис не отвечает

**Симптом:** `/health` не отвечает либо возвращает ошибку.

1. Проверить HTTP-ответ: `curl -fsS --max-time 5 http://127.0.0.1:8000/health`
2. Проверить состояние контейнеров: `docker compose ps`
3. Проверить последние логи приложения: `docker compose logs --tail=100 app`
4. Проверить, что выбранный образ существует и текущий тег задан: `grep '^APP_IMAGE=' .env` (не выводите весь `.env` в общий чат).
5. Если проблема началась сразу после релиза — вернуть в `.env` предыдущий проверенный `APP_IMAGE=ghcr.io/<OWNER>/<REPO>:v<PREVIOUS>` и выполнить:
   `docker compose pull app && docker compose up -d --no-build`
6. Подтвердить восстановление: `curl -fsS --max-time 5 http://127.0.0.1:8000/health`, затем `docker compose ps` и `docker compose logs --tail=50 app`.
7. Если `/health` не восстановился за 10 минут, либо затронуты данные/безопасность — эскалировать владельцу сервиса и дежурному платформы. Передать время начала, commit/tag и обезличенные логи.

## Приложение живо, но сообщения не читаются или не записываются

**Симптом:** `/health` возвращает `{"status":"ok"}`, но `GET /messages` или `POST /messages` завершается ошибкой.

1. Проверить контейнеры и healthcheck БД: `docker compose ps`
2. Проверить последние логи базы: `docker compose logs --tail=100 db`
3. Проверить логи приложения: `docker compose logs --tail=100 app`
4. Проверить повторно API: `curl -i --max-time 5 http://127.0.0.1:8000/messages`
5. Если БД не healthy, безопасно перезапустить только сервисы, не удаляя volume: `docker compose up -d db app`
6. Если сбой начался после релиза — откатить `APP_IMAGE` на предыдущий SemVer-тег по процедуре выше. Не выполнять `down -v`, `DROP TABLE` и ручное удаление данных.
7. Если БД остаётся unhealthy более 10 минут, есть ошибки диска/коррупции либо неизвестно состояние данных — остановить дальнейшие изменения и эскалировать владельцу сервиса/БД. Сохранить логи и время ошибки; не прикладывать секреты.

## Выпуск новой версии

1. Убедиться, что CI зелёный и образ версии опубликован в GHCR.
2. Записать текущий `APP_IMAGE` как точку возврата.
3. Указать новый точный тег в серверном `.env`, выполнить `docker compose pull app && docker compose up -d --no-build`.
4. Проверить `docker compose ps`, `curl -fsS http://127.0.0.1:8000/health` и `curl -fsS http://127.0.0.1:8000/messages`.
5. При ошибках выполнить откат на сохранённый предыдущий тег и проверить health снова.

## Совместимость схемы и откат

Схема `messages(id, author, text)` создаётся при старте через `CREATE TABLE IF NOT EXISTS`; существующая таблица этим выражением не переименовывается и не удаляется. Поэтому текущий откат к предыдущему образу не зависит от обратного преобразования схемы. Если схема будет расширяться, сначала добавлять nullable-колонки/таблицы, которые старый код игнорирует; переключить код отдельным релизом и только после вывода старого кода из эксплуатации удалять старые поля (expand-contract). Данные PostgreSQL не откатываются вместе с образом.
